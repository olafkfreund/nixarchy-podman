# Spec: The menu ignores the screen it is drawn on

## Design

### The complaint decomposes into three problems, and only two are code

The intent established by measurement that all three monitors are `scale=1`,
`devicePixelRatio` is 1 everywhere, and no `base-size` is set, so
`Style.fontBaseSize` is its default 12. Working out what each available lever
actually does separates the report into three independent problems.

**Problem A: everything is too small.** This is a theme setting, and the
arithmetic says so. `Style.effectiveSpacingScale` is
`spacingScale * fontScale`, and `fontScale` is `fontBaseSize / 12`, so
`base-size` scales text, spacing and the card together:

| `base-size` | body text | `viewWidth` | card width | of 2560 | of 1920 |
| --- | --- | --- | --- | --- | --- |
| 12 (today) | 12px | 680 | 986px | 39% | 51% |
| 14 | 14px | 793 | 1150px | 45% | 60% |
| 16 | 16px | 907 | 1315px | 51% | 68% |
| 18 | 18px | 1020 | 1479px | 58% | 77% |

One line in the theme, no code, and it fixes the bar and every other plugin at
the same time. **This should be tried before anything below is written.** If it
resolves the complaint, the remaining scope is problems B and C only — and
those are worth fixing regardless, because they are defects rather than
preferences.

**Problem B: the menu does not reflow.** `Menu.qml:154-156` lays the view out
at its natural size and then draws it 1.45 times larger with `scale:`. Wrap
points and elide decisions are computed before the transform and stretched
after it, so a label that would fit at the displayed size still elides. Real,
independent of A, and not fixable by any theme setting.

**Problem C: the menu does not adapt between the owner's own monitors.**
`viewWidth` is `Style.space(680)` whatever screen it opens on, so the card is
the same width on the 1920 panel and the 2560 ones. Note a correction to the
intent: the `Style.space(560)` list cap is *not* a constant — it scales with
the theme like everything else. It is screen-blind, which is the actual
defect, not fixed.

### B: adopt the fleet's `textScale` + `px()`

`nixarchy-pkg` and `nixarchy-flatsnap` both solve this with a layout-time
multiplier and no transform, verified by reading the built plugins. The
mechanism, from `nixarchy-pkg`:

```qml
readonly property real textScale: 1.45
function px(base) { return Math.round(base * root.textScale) }
...
font.pixelSize: root.px(Style.font.body)
```

**What it scales, and what it does not.** `px()` is applied to font sizes
only. Spacing keeps plain `Style.space(14)`, `Style.space(40)` — `Card.qml:203`
mixes the two in one expression. This is not a like-for-like replacement for
podman's transform, which magnifies padding, gaps, borders and radii along
with the text. **Adopting it will make the menu visually denser than it is
today**, and that is a change the approver is agreeing to, not an incidental
detail.

The spec recommends adopting it unchanged anyway, for a reason better than
consistency: spacing is not left unscaled in absolute terms. It already
follows the theme through `effectiveSpacingScale`. So the resulting model is
coherent — **spacing follows the theme; text gets an additional
viewing-distance boost because a full-screen surface is read from further
away.** That is what `uiScale`'s comment at `Menu.qml:32-35` always claimed to
be doing, and the transform was a blunt way of doing it.

**Cost, measured.** 23 `pixelSize:` sites across `PodmanView.qml` (7),
`ResourceList.qml` (8), `TabStrip.qml` (3) and `ShortcutSheet.qml` (5). Each
becomes `root.px(Style.font.X)`. Four components gain
`property real textScale: 1.0` and the `px` function, and four pass-downs
thread it.

**The wire already exists.** `fontFamily` is threaded exactly this way today —
`Menu.qml` and `Panel.qml` set it on `PodmanView`, which passes it to
`ResourceList` and `TabStrip` (`ResourceList.qml:31,165`, `TabStrip.qml:18`).
`textScale` goes alongside it, at every site that already carries
`fontFamily`. No new pattern.

The default of `1.0` matters: `Panel.qml` sets nothing and the popup keeps its
current size, because a bar popup is read at arm's length. Only `Menu.qml`
passes `1.45`, and `Menu.qml:125-127,154-156,162` lose the transform and the
inverse-width arithmetic entirely — the view fills its frame like any other
item.

### C: derive the width from the screen

```qml
readonly property int viewWidth: Style.space(
  root.targetScreen ? Math.max(560, Math.min(820, Math.round(root.targetScreen.width / 3.6)))
                    : 680)
```

On the 1920 panel that is `Style.space(533 → clamped 560)`; on the 2560 ones
`Style.space(711)`. The existing `panel.width * 0.9` cap stays as the outer
bound. The clamp keeps a very small screen readable and a very large one from
becoming a letterbox.

**The divisor and the bounds are taste, not arithmetic**, and the approver
should say what looks right rather than accept these numbers. They are chosen
to leave the 2560 case close to today's 680 so the change is mostly felt on
the 1920 panel, which is the one currently worst served.

`listMaxHeight` keeps its `Style.space(560)` ceiling. It is already bounded by
`panel.height * 0.85` and scales with the theme; adding a second screen-derived
expression for a value that already has one screen-derived bound is
complication without benefit.

### Not in scope

No scale setting in `manifest.json`. `base-size` already exists, is
shell-wide, and is where a user who wants things bigger should go. A
per-plugin override would duplicate it and be one more thing to explain.

Deriving anything from `devicePixelRatio` is rejected outright — see below.

## Alternatives rejected

**Derive `uiScale` from `targetScreen.devicePixelRatio`.** Rejected twice
over. On this hardware it evaluates to 1.0 on all three monitors, *smaller*
than today's 1.45 and the opposite of the report. And it is wrong in
principle: `ShellScreen.width` is logical with DPR already divided out, and Qt
applies DPR at rasterisation, so multiplying a layout factor by it applies it
twice. `uiScale` encodes viewing distance, not pixel density.

**Keep the transform and fix only the constants.** Two lines and it addresses
problem C. Rejected because it leaves B, and B is the defect that cannot be
worked around by any setting.

**Scale spacing with `px()` too, to preserve today's appearance.** Rejected:
it diverges from the two plugins that already solved this, for the sake of
preserving a look that was itself an artefact of the transform. If the
approver dislikes the denser result, this is the fallback — it is a wider
change, not a harder one.

**Do nothing in code and only raise `base-size`.** Rejected as a complete
answer, though it is the correct *first* action. It cannot fix reflow and
cannot make the menu adapt between monitors.

## Risks

- **The menu will look different**, denser in its text-to-space ratio. This is
  the change most likely to be rejected on sight, which is why the spec states
  it plainly rather than describing the work as a refactor.
- **23 mechanical edits is where a typo hides.** A missed site keeps its
  unscaled size and will read as a slightly-wrong row rather than an error.
  Verification must enumerate the sites, not sample them.
- **Captures.** Every menu still and recording in `docs/img/` becomes wrong:
  `menu.png`, `rec-menu.webm`, `rec-menu.mp4`, and `demo.gif` if it shows the
  menu. That is the largest cost in this issue. `docs/img` is at 5,761,828
  bytes, 69% of the 8 MB budget, so replacements must not grow.
- **`textScale` defaulting to 1.0 means a forgotten pass-down silently leaves a
  component unscaled** rather than failing. The verification checks the popup
  and the menu side by side for exactly this.
- **No packaging or host risk.** No new file; `flake.nix`'s `files` list is
  untouched.

## Verification

1. `node tests/run.js` and `nix flake check` green. Neither exercises QML
   layout, so they prove only that nothing else broke.
2. `grep -c 'pixelSize:'` in each of the four drawing files equals the count of
   `root.px(` in the same file — every site converted, none missed.
3. `grep -rn 'scale:' *.qml` returns nothing, matching the two reference
   plugins.
4. Live, and this is the real verification:
   - Open the menu on DP-2 (2560) and on HDMI-A-1 (1920). The card should be a
     sensible fraction of each, not the same absolute width.
   - Open the menu and the bar popup side by side showing the same container
     at the same theme size. The popup is the untransformed control: text
     should be larger in the menu and identical in weight and crispness.
   - Filter to a container with a long name and confirm the label wraps or
     elides at the size actually displayed, which is what the transform
     prevented.
   - Press `?` and confirm the shortcut sheet fits, with an eye on #17, which
     reports it overflowing a short card.
5. Retake `menu.png` and the menu recordings, check every frame, and confirm
   `du -sb docs/img` has not grown past 8 MB.

Before any of this: set `[font] base-size` in the theme and decide whether the
complaint survives. That answer determines whether this issue ships as
written or shrinks to B alone.
