# Spec: Call it 1.0

## Design

### The bump is one line

`manifest.json:5` is the only place a version appears. `flake.nix:11` reads
it with `builtins.fromJSON` and `:32` builds the store path from it, so
changing that line renames the derivation and nothing else needs touching.
`README.md` and `docs/usage.md` carry no version string.

```json
  "version": "1.0.0",
```

`nix build` after the change must produce `…-nixarchy-podman-1.0.0`, which is
the check that the flake really is reading it.

### Order: merge, verify, then tag

The intent made this a constraint and it shapes everything else. A tag is the
thing people pull and moving one afterwards is awkward, so:

1. the bump merges to `master` through a normal PR;
2. CI passes on `master` at that commit;
3. `nix build` locally confirms the store path carries `1.0.0`;
4. **only then** `git tag -a v1.0.0` on that exact commit, and the release is
   cut from the tag.

An annotated tag, not lightweight: a release tag should carry a message and
an author.

### The three open questions

**The #38 videos do not block — but the notes say so.** Six recordings plus
`demo.gif` still show a menu that no longer looks like that, because #22, #30
and #17 changed it. That is a real cost to the shop window, and it is not a
reason to withhold a version number: the videos need a driven desktop and the
software is ready now. #38 stays open and the release notes point at it, so
someone comparing the site against what they installed knows why they differ.

**It is marked latest, not pre-release.** The approver has called it 1.0. A
pre-release flag would contradict that through a checkbox rather than a
conversation, and it would hide the caveat in metadata instead of putting it
in the notes where it is read. The unverified path goes in the notes, plainly.

**Wiring p620 and razer does not block.** That is deploying to hosts, which is
downstream of having a version to deploy — and a tag makes it easier, because
those hosts can pin one instead of tracking `master`.

### The release notes

Written, not generated. Twelve issues need a narrative, and a list of commit
subjects would not tell a reader what changed about the plugin.

Three sections:

1. **What changed**, grouped by what it means to someone using it, not by
   issue number. The destructive path asking first leads.
2. **What was verified live**, naming the machine: the menu at a raised
   `base-size`, the `ipv6` badge lighting for the first time, the card at 47%
   of a 2560 panel, the confirmation dialogs screenshotted before being
   escaped, the podman state diffed identical afterwards.
3. **What was not verified.** #19's stop-all confirmation has never been seen
   by a human — it needs a pointer click and no input daemon was available.
   This is the most safety-relevant change in the release and it is stated in
   its own section, not softened into a footnote. Also: the site's videos are
   stale, and #37's post-restart tab behaviour was never cleanly confirmed.

No binary artifact is attached. The plugin is installed by cloning the repo
or through the flake; there is nothing to download that the tag does not
already give.

## Alternatives rejected

**Tag first, then fix anything CI finds.** Inverts the constraint the intent
set, and a moved tag is worse than a late one.

**Generate notes from commit subjects.** Forty-two `feat`/`fix` subjects is a
changelog, not a release note. A reader wants to know the prune button used to
lie, not that `canPrune` reuses `pruneTargets`.

**Mark it pre-release to hedge the unverified path.** Hides a caveat in
metadata. The notes say it instead.

**Hold 1.0 until #19 is clicked once.** This was my recommendation and the
approver has decided otherwise. Recorded here so the decision is visible
rather than silently reversed; the notes carry the consequence.

**Bump to 0.3.0.** Also rejected by the approver. Noted for the same reason.

## Risks

- **A release is outward-facing and hard to retract.** People may install it
  between publication and any correction. This is why the tag comes after
  green CI rather than before.
- **The store path changes**, so anyone pinning
  `…-nixarchy-podman-0.2.0` by hash gets a different path. That is what a
  version bump is for, and nothing in this repository pins it.
- **The stills and videos disagree on the site.** Stated in the notes; #38
  remains open.
- **`v1.0.0` sets an expectation of stability** that the follow-ups in
  AGENTS.md may yet disturb — particularly the two inlined shell components
  from #30, which are deliberate debt waiting on an upstream change.

## Verification

1. `jq -r .version manifest.json` is `1.0.0`.
2. `nix build` produces a store path ending `-nixarchy-podman-1.0.0`.
3. `node tests/run.js` green at 175, `nix flake check` green.
4. CI green on the PR **and** on `master` after merge.
5. `git tag -a v1.0.0` points at that `master` commit —
   `git rev-parse v1.0.0^{}` equals `git rev-parse master`.
6. `gh release view v1.0.0` shows the written notes, marked latest, with the
   "not verified" section present.
7. `omarchy plugin validate` on a fresh clone of the tag still passes, since
   that is how people will install it.
