# Plan: The menu ignores the screen it is drawn on

## The approved decisions, carried over

**Problem A (everything is too small) is a theme setting, not code.**
`effectiveSpacingScale = spacingScale * fontScale` and `fontScale =
fontBaseSize / 12`, so `[font] base-size` scales text, spacing and the card
together: 12 to 16 takes body text from 12px to 16px and the card from 986px
to 1315px, across the whole shell. Nothing in this plan substitutes for it.

**Problem B (no reflow) is knowingly left unfixed.** The transform computes
wrap and elide before magnifying, so labels elide against the wrong width.
The available fix — the fleet's `textScale` + `px()` — does not transfer:
`ConfirmDialog` hardcodes `Style.font.title` and `caption`, `PanelHero`
hardcodes title, body and caption, and `TextField` has no size property. Under
`px()` the confirmation question would stay at theme size while the list grew
1.45x, shrinking the safety surface. `Menu.qml:32-35` already recorded the
transform as a deliberate choice over "a size knob threaded through every
font". It stays, and gains a comment saying why so the next reader does not
undo it.

**Problem C (no adaptation between monitors) is what this plan fixes.**

## Steps

One commit per step, citing the step number and `#22`.

1. **`Menu.qml`: derive `viewWidth` from the target screen.**

   **Deviation from the approved spec.** The spec proposed
   `Math.max(560, Math.min(820, Math.round(targetScreen.width / 3.6)))` and
   justified it as helping the 1920 panel, "the one currently worst served".
   Both the formula and the reasoning were wrong, and computing them showed
   it:

   | screen | today | spec's `/3.6` |
   | --- | --- | --- |
   | 1920 | 986px (51%) | 812px (42%) — *narrower* |
   | 2560 | 986px (39%) | 1031px (40%) — barely moves |

   The 1920 panel is the one the card already fits well on; the 2560 screens
   are where it looks lost. The spec's formula shrank the good case and left
   the bad one. Replaced with a constant fraction bounded for readability,
   which is what "follows the screen" should mean:

   ```qml
   // A constant slice of whatever screen it opens on, bounded so a small
   // display stays usable and a very wide one does not become a letterbox.
   // The bounds are theme units and grow with [font] base-size; the target is
   // a fraction of real screen pixels, so it is not theme-scaled twice.
   readonly property int viewWidth: {
     if (!root.targetScreen) return Style.space(680)
     var target = Math.round(root.targetScreen.width * 0.46 / root.uiScale)
     return Math.max(Style.space(560), Math.min(target, Style.space(820)))
   }
   ```

   Computed results, with the existing `panel.width * 0.9` cap still outermost:

   | screen | base 12 | % | base 16 | % |
   | --- | --- | --- | --- | --- |
   | 1366 | 812px | 59% | 1083px | 79% |
   | 1920 | 883px | 46% | 1083px | 56% |
   | 2560 | 1178px | 46% | 1178px | 46% |
   | 3840 | 1189px | 31% | 1585px | 41% |

   → verify by computing the four cases and comparing to this table.

2. **`Menu.qml`: comment the transform with its trade-off**, replacing the
   existing note at `:152-153`:

   ```qml
   // Laid out at its natural size, then drawn uiScale times larger; input is
   // mapped through the same transform, so clicks still land. The cost is
   // that wrap and elide are computed before the magnification -- a long name
   // elides against the small width (#22). A layout-time multiplier would fix
   // that, but ConfirmDialog, PanelHero and TextField expose no font size, so
   // it would leave the confirmation question at theme size while the list
   // around it grew. Uniform beats crisp here. Revisit if those gain a
   // fontSize property.
   ```

   → verify by reading it back.

3. **Open the upstream follow-up** in AGENTS.md's "Known follow-ups", so the
   condition for revisiting B is recorded where the other deferred work lives:

   ```markdown
   - Offer `fontSize` properties for `PanelHero`, `TextField` and
     `ConfirmDialog` upstream. Until they exist, the menu must magnify with a
     transform rather than a layout-time multiplier, and long names elide
     against the pre-transform width (#22).
   ```

   → verify by reading it back.

## Tests

Live, and this is the real verification:

1. Open the menu on DP-2 (2560x1440) and on HDMI-A-1 (1920x1080). The card
   should be a similar *fraction* of each, not the same absolute width —
   roughly 46% on both, where today it is 39% and 51%.
2. Trigger a confirmation in the menu; the question should be the same size
   relative to the list as it is today. This is the regression the rejected
   approach would have introduced.
3. Press `?`; the shortcut sheet should still fit, with an eye on #17.
4. Set `[font] base-size = 16` in the theme, reopen, and confirm everything
   grows together and the card stays near 46% on the 2560 panel.

## Rollback

One property and two comments. Reverting step 1 restores
`Style.space(680)` and today's behaviour exactly. Nothing else depends on it;
`card.width` and `listMaxHeight` keep their existing expressions.
